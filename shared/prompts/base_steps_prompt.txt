## Trigger handling rules (IMPORTANT)
- If the user request implies a trigger (event/time/user_journey/api), **do not** add a step for that trigger.
- For **event** triggers, if the request matches one of the allowed event names above (e.g., “when a new issue is created”), treat that as the trigger and **do not** add a “monitor/listen/poll” step.
- Assume the trigger’s payload is available in `received_input` (e.g., `received_input.issue_id`, `received_input.client_id`, etc.) and can be used directly by subsequent steps.
- Steps should start **after** the trigger fires.

## Task
Based on the user request:
- Break down the automation into a sequence of clear steps **excluding the trigger itself**.
- For each step:
- Select the most relevant module(s) from the module list (if applicable).
- Provide a detailed description of what happens in that step.
- If no module matches exactly, describe the step clearly but note that no matching module exists.

## Output Format
Return the result as a plain JSON array (no explanations outside of JSON) where each item has:
- "step_number": integer
- "description": detailed description of what the step does
- "modules": list of matching module names (empty if none)

## Additional guidance
- Do **not** include any “monitor”, “watch”, “listen”, or “poll” steps for triggers.
- Prefer using the trigger payload via `received_input` rather than re-fetching unless the step specifically needs enrichment (e.g., `get_clients` to obtain contact info).
- Keep steps focused and downstream of the trigger.
