Rules (IMPORTANT):
1) The trigger is NOT a workflow step. Do not add “monitor/listen/poll” steps.
2) Assume the trigger payload is available in the workflow as {{ received_input.* }}.
- For event triggers, map TRIGGER.payload fields directly to {{ received_input.* }} (e.g., {{ received_input.issue_id }}).
3) Interpret ALL_STEP_TEXT and select the most appropriate module(s) from MODULE_DEFINITIONS.
4) Construct Automatou workflow step JSON for all steps (per docs).
- Each step MUST include: "id" (snake_case, not starting with a number), "module", "input".
- The id should be unique for all steps.
- Optional: "name", "description", "allow_fail", "config", "debug", "skip_output_log", "error_workflow" if warranted.
5) Map inputs exactly as per the module spec (correct names/types). Prefer minimal valid inputs.
6) Use templating to reference prior data when needed:
- {{ received_input.* }} for trigger payload
- {{ <previous_step_id>.* }} for outputs of earlier steps (if any are already present in the workflow)
7) If ALL_STEP_TEXT implies multiple actions with multiple modules, emit multiple step objects in run order.
8) If no suitable module exists, DO NOT fabricate one; instead return exactly:
{
    "needs_module": true,
    "reason": "short explanation of what module is missing for CURRENT_STEP_TEXT",
    "suggested_keywords": ["keywords to re-query for a better module"]
}

Output format (STRICT):
- Output ONLY a JSON array.
- If you produced steps, the array contains 1..N Automatou step objects.
- If you couldn't produce any step because no module fits, the array contains exactly one object with "needs_module": true.
